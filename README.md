# WorkAid · 劳动法律援助助手

面向劳动者的中文法律信息助手。描述遇到的劳动纠纷，它会检索法条与类似案例、逐条核验回答里的引用、按你所在地整理维权路径，并把回答一段一段流式展示出来。

> **这不是律师，也不构成法律意见。** 它提供一般法律信息，帮你理清问题、找到依据和该联系的机构。重大事项请咨询律师或法律援助中心。

**在线体验**：本仓库的 GitHub Pages 站点是一个**回放演示**。它播放事先从真实系统录制下来的几个场景，不调用任何模型。完整系统需要本地或 Codespaces 运行，见下文。

## 它做什么

- **流式回答**：思考过程（理解问题 → 检索 → 综合 → 核验）实时可见，答案逐字出现。
- **引用核验**：回答里每个《法名》第X条和案号都与本地法规库、案例库核对。编造的条号会被删除并标注，已废止的法律会被标注。
- **案情档案**：自动整理案件类型、关键事实和还缺哪些信息，每轮最多追问三个问题；金额和期限由程序计算，不由模型计算。
- **维权路径**：按案件类型与所在城市列出该找的机构（劳动保障监察、仲裁委、法院、法律援助）、需要带的材料，以及时效。
- **隐私**：手机号、证件号、银行卡号等在进入系统前即被替换，原文不落库、不发给模型；姓名、单位、住址默认也脱敏，只有用户明确要求“记住”才保存。
- **长期记忆**：从对话里自动归纳稳定背景（所在地、行业、合同与社保状态等），可逐条删除，也可一键清空。

## 架构

```
浏览器（React + Vite）
  │  POST /api/chat/stream   (Server-Sent Events)
  ▼
FastAPI ── 入口脱敏 ──► LangGraph 图（共享状态）
                          ├─ route        意图路由（规则优先，模型兜底）
                          ├─ statute      法条检索 ─┐
                          ├─ case         类案检索  ├─► synthesize ─► 引用核验 ─► 案情梳理
                          └─ aid          维权路径 ─┘        │
                                                  流式 token ◄┘
存储：SQLite（会话、画像、案情档案、摘要）
语料：rag/data（法律法规 JSON） → SQLite FTS5 索引
检索：双路并发召回（ChromaDB 语义检索 ∥ SQLite FTS5 BM25）→ RRF 融合取 Top-K → bge-reranker 精排取 Top-N → 相关度门槛
```

关键设计：

| 关注点 | 做法 |
|---|---|
| 不让模型编造 | 法条、案号逐条核验；金额、期限由 `calc.py` 计算并标注依据 |
| 隐私 | `privacy.py` 在唯一入口脱敏，存储层再脱敏一次，外发请求经测试确认不含敏感值 |
| 可降级 | 没有模型密钥时走规则路径；没有向量索引时跳过向量路；精排不可用时退回启发式排序；外部服务超时即降级，不阻塞回答 |
| 可复现 | 语料由 JSON 重建数据库；评测脚本可重跑；录制脚本从真实后端生成演示数据 |
| 流式 | 后端用 LangGraph 的 `custom` 流推送 token；前端用 `fetch` 读取 SSE，不依赖第三方库 |

## 检索链路

```
用户问题
  │  词典改写（口语 → 法律术语）、生成查询变体
  ▼
┌─ 路 A：ChromaDB 语义检索 ── bge-m3 向量，余弦距离，取 VECTOR_TOP_K 条/查询
└─ 路 B：SQLite FTS5 BM25 ── trigram 分词，取 BM25_TOP_K 条/短语        （两路并发）
  │
  ▼
RRF 融合：score = Σ 权重 / (RRF_K + 排名)，RRF_K = 60，取前 RRF_TOP_K 条
  │
  ▼
bge-reranker-v2-m3 精排：对融合结果逐条打分；最终分 = RERANK_WEIGHT × bge 分 + (1 − RERANK_WEIGHT) × 启发式分
  │  精排不可用 → 只用启发式分（概念覆盖、IDF 加权、BM25、向量相似度等特征）排序
  ▼
两道门槛：精排分数过 RERANK_MIN_SCORE，且启发式分数过相关度门槛 → 都过才保留
  ▼
Top-N（默认 5，每部法规最多 3 条）→ 与用户问题一起放入回答模型的上下文
```

精排与启发式分数共同决定排序，并且两道门槛都要通过：精排只能给出相对顺序，不能判断库里是否真有相关条文，所以启发式门槛始终生效。两道门槛都不过时，系统会说明本地未检索到，并依次尝试远端兜底。

### 参数与取值

| 参数 | 默认值 | 含义 |
|---|---|---|
| `VECTOR_TOP_K` | 20 | 路 A 每个查询向量取回的条数 |
| `BM25_TOP_K` | 10 | 路 B 每个短语取回的条数 |
| `RRF_K` | 60 | RRF 的平滑常数 |
| `RRF_TOP_K` | 30 | 融合后送入精排的候选数 |
| `RERANK_WEIGHT` | 0.25 | 排序中 bge 分数的权重，其余为启发式分数；1.0 即纯精排排序，0 即纯启发式排序 |
| `RERANK_MIN_SCORE` | 0.1 | 精排分数门槛 |
| 精排 Top-N | 5 | 最终放入回答上下文的条数（由调用方传入） |

`VECTOR_TOP_K`、`BM25_TOP_K`、`RRF_TOP_K` 与 `RERANK_WEIGHT` 由 `eval/tune_retrieval.py` 和权重扫描确定，方法见下一节。

### 如何确定这些参数

1. **先固定评测集。** 开发集（33 题）用来选参数，留出集（15 题）只用来报告，不参与选择。
2. **网格扫描。** 在 `VECTOR_TOP_K ∈ {10, 20}`、`BM25_TOP_K ∈ {10, 20, 40}`、`RRF_TOP_K ∈ {30, 60, 120}` 上，分别以纯精排与纯启发式两种排序各跑一遍，共 18 组。
3. **权重扫描。** 固定 k 值，在 `RERANK_WEIGHT ∈ {0, 0.25, 0.5, 0.75, 1.0}` 上扫描，同样只用开发集选择。
4. **选择规则。** 以开发集的 hit@5 为主、MRR 为次；并列时取更小的 k 或更小的 bge 权重，因为它们更快、更省精排调用。
5. **为什么 k 不大。** 路 A 和路 B 的 k 决定候选覆盖面；`RRF_TOP_K` 是精排的输入上限，超过某个值后精排要处理更多噪声，收益趋近于零。扫描中候选池从 30 增到 60、120，没有带来稳定提升。

### 实测结果

| 配置 | 开发集 hit@1 / hit@5 / MRR | 留出集 hit@1 / hit@5 / MRR |
|---|---|---|
| **默认**：RERANK_WEIGHT=0.25，VECTOR_TOP_K=20，BM25_TOP_K=10，RRF_TOP_K=30 | 0.613 / 0.935 / 0.742 | 0.571 / 0.786 / 0.667 |
| 纯精排排序（RERANK_WEIGHT=1.0） | 0.226 / 0.839 / 0.449 | 0.429 / 0.500 / 0.443 |
| 纯启发式排序（RERANK_WEIGHT=0，VECTOR_TOP_K=10，BM25_TOP_K=20） | 0.742 / 0.903 / 0.809 | 0.643 / 0.857 / 0.720 |
| 改造前的基线（numpy 向量，旧的精排混合） | — / 0.903 / — | — / 0.786 / — |

- 默认配置连续三次冷启动（每次清空精排缓存）结果完全一致。
- 纯启发式排序不调用精排 API，结果可精确复现。
- **结论：** 在本项目的标注上，纯 bge 排序明显弱于启发式排序，而把两者按 1:3 混合后，开发集 hit@5 从 0.871 提升到 0.935。但留出集上，混合的 0.786 低于纯启发式的 0.857。
- **留出集的解读：** 留出集只有 15 题，每题相当于 0.067 的命中率，差异是一到两道题的结果。开发集是按规则选出的参数，它在留出集上的表现是更诚实的估计，但两者的样本都太小，不能证明混合一定优于纯启发式。
- **注意：** 标注由开发者本人编写，不是律师标注，数字只能说明方向。用于真实场景前，应由律师重新标注后再评估。

## 运行

需要 Python 3.11+、Node 20+。

```bash
# 后端
cp .env.example .env            # 可选：填入 OPENAI_API_KEY 等，不填也能运行（规则路径）
pip install -e ".[dev]"         # 或 uv sync --extra dev
python agent.py                 # http://127.0.0.1:8081

# 前端（另开一个终端）
npm install
npm run dev                     # http://127.0.0.1:5173，代理 /api 到后端
```

首次启动会从 `rag/data` 的法规 JSON 自动构建 SQLite 索引（约 20 秒，之后复用）。

**没有任何密钥也能跑**：法条检索、类案检索、案情档案、计算和脱敏都是本地规则完成的；只是回答改为模板拼接，而不是模型写的。

### 长期记忆与缓存

聊天记录、摘要和用户长期画像共用记忆数据库。设置 `MEMORY_DATABASE_URL` 后使用 PostgreSQL；未设置时回退到 `DATABASE_PATH` 指定的 SQLite 文件。首次启动会在目标数据库中创建所需表。

Redis 仅用于可选的通用答案缓存。设置 `REDIS_URL` 启用，留空则关闭；Redis 不可用时请求会按未命中继续处理，不影响回答。生产部署请为 PostgreSQL 使用独立数据库和专用账号，并通过部署环境注入连接串。

### 配置模型（可选）

任何 OpenAI 兼容服务都可以：

```
OPENAI_API_KEY=...
OPENAI_BASE_URL=https://api.example.com/v1
OPENAI_MODEL=...
# 服务商特有开关，例如 DeepSeek 关闭推理阶段以加快首字：
OPENAI_EXTRA_BODY={"thinking":{"type":"disabled"}}
```

可选的向量召回与重排同样只需填入 `EMBEDDING_*`、`RERANK_*`。向量索引需要运行 `python -I scripts/build_vector_index.py` 生成，存放在 `rag/cache/chroma`（它派生自语料，不随仓库提供）。

### 在线体验（Codespaces）

仓库带有 `.devcontainer`，在 GitHub 上点击 **Code → Codespaces** 即可得到一个运行中的完整系统。把模型密钥放在 Codespaces 的 Secrets 里，不要写进代码。

## 演示站点（GitHub Pages）

`VITE_DEMO=1 npm run build` 生成一个不需要后端的静态版本。场景回放来自 `scripts/record_demo.py`：它驱动**真实的** `/api/chat/stream`，把事件序列与最终回答存为 `frontend/public/demo/*.json`。因此演示里的每个字都是系统真实生成的，只是不再重新计算。

重新录制：`python -I scripts/record_demo.py`（需要配置模型）。

## 语料与数据

- `rag/data/`：法律法规的 JSON 语料（来自公开来源）。已知部分法条在采集时被切坏（跨行引用被误分条），检索会跳过残片并标注截断；`eval/audit_corpus.py` 可列出受影响的法律。
- `data/cases.jsonl`：示例案例，来自公开的裁判文书与典型案例通报，经脱敏扫描。
- `data/institutions.jsonl`：示例机构，目前只有北京的少量条目，已核验来源；其他城市会如实提示“暂未收录”。
- `data/scripts.jsonl`：话术模板，每条标注审核状态。
